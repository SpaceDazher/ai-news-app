**Логика Страницы Аутентификации:**

1.  **При запуске приложения:** Проверяется статус аутентификации пользователя (например, наличие валидного токена).
2.  **Если пользователь не аутентифицирован:** Происходит автоматическое перенаправление (redirect) на страницу аутентификации (`/auth` или `/login`).
3.  **Если пользователь аутентифицирован:** Он остается в приложении или перенаправляется на главную страницу (например, на дашборд или страницу просмотра текста).

Это стандартный и рекомендуемый паттерн для SPA.

## Документация: Страница Аутентификации (`AuthPage`)

**Файл:** `docs/pages/auth.md` (или секция в `docs/pages-documentation.md`)

**1. Назначение Страницы**

Страница Аутентификации (`AuthPage`) является точкой входа для неавторизованных пользователей. Она предоставляет интерфейс для:

*   **Регистрации** новых пользователей.
*   **Входа** существующих пользователей в систему.

**2. Пользовательский Поток (User Flow)**

*   Пользователь, не имеющий активной сессии, при попытке доступа к защищенным страницам приложения, автоматически перенаправляется на `/auth`.
*   На странице `/auth` пользователь видит форму (по умолчанию, например, форма входа).
*   Пользователь может переключиться между формой входа и формой регистрации (например, с помощью вкладок или ссылки "Еще нет аккаунта? Зарегистрируйтесь").
*   **Для Входа:** Пользователь вводит свои учетные данные (email/пароль) и нажимает кнопку "Войти". Система проверяет данные и, в случае успеха, аутентифицирует пользователя (сохраняет токен) и перенаправляет его на основную страницу приложения (например, `/dashboard`). В случае ошибки отображается соответствующее сообщение.
*   **Для Регистрации:** Пользователь вводит необходимые данные (email, пароль, подтверждение пароля) и нажимает кнопку "Зарегистрироваться". Система создает нового пользователя. В зависимости от логики, пользователь может быть сразу аутентифицирован и перенаправлен, или ему будет предложено войти с новыми учетными данными. В случае ошибки (например, email уже занят) отображается сообщение.
*   (Опционально для MVP): Может присутствовать ссылка "Забыли пароль?" для запуска процесса восстановления пароля.

**3. Примерный UI (Концепция)**

Страница должна быть минималистичной и понятной:

*   **Заголовок:** "Вход" или "Регистрация" (в зависимости от активной формы).
*   **Переключатель Форм:** Вкладки ("Вход" | "Регистрация") или текстовая ссылка для переключения.
*   **Форма Входа:**
    *   Поле ввода "Email" (тип `email`, обязательное).
    *   Поле ввода "Пароль" (тип `password`, обязательное).
    *   Кнопка "Войти" (отправка формы).
    *   (Опционально) Ссылка "Забыли пароль?".
*   **Форма Регистрации:**
    *   Поле ввода "Email" (тип `email`, обязательное).
    *   Поле ввода "Пароль" (тип `password`, обязательное, с требованиями к сложности).
    *   Поле ввода "Подтвердите пароль" (тип `password`, обязательное, должно совпадать с полем "Пароль").
    *   Кнопка "Зарегистрироваться" (отправка формы).
*   **Область для Сообщений об Ошибках:** Отображение ошибок валидации или ответа сервера.

**4. Архитектура FSD и Компоненты**

*   **Страница (`pages/auth/AuthPage.tsx`):**
    *   Отвечает за рендеринг `AuthFeature`.
    *   Может содержать логику проверки статуса аутентификации при монтировании и перенаправления, если пользователь уже вошел в систему (используя хук `useAuth` из `shared` или `entities`).

*   **Фича (`features/auth/AuthFeature.tsx`):**
    *   Основной контейнер логики аутентификации.
    *   Управляет состоянием активной формы (вход или регистрация).
    *   Управляет состоянием полей ввода форм (используя `useState` или библиотеку управления формами, например, `react-hook-form`).
    *   Обрабатывает отправку форм (`onSubmit`):
        *   Выполняет клиентскую валидацию данных.
        *   Вызывает соответствующие функции API (см. раздел API Design).
        *   Обрабатывает ответы API (успех/ошибка).
        *   В случае успеха: обновляет состояние аутентификации (через Redux или Auth Context) и инициирует перенаправление (через React Router).
        *   В случае ошибки: отображает сообщение об ошибке.
    *   Рендерит либо `LoginForm`, либо `RegisterForm` в зависимости от состояния.
    *   Рендерит переключатель форм.

*   **UI Компоненты Фичи (`features/auth/ui/`):**
    *   `LoginForm.tsx`: Презентационный компонент формы входа. Получает состояние полей, обработчики изменений (`onChange`) и обработчик отправки (`onSubmit`) через props от `AuthFeature`. Использует shared-компоненты `Input` и `Button`.
    *   `RegisterForm.tsx`: Презентационный компонент формы регистрации. Аналогичен `LoginForm`.

*   **Сущность (`entities/user/` - опционально для UI, но важно для логики):**
    *   Может содержать модель пользователя (`IUser`).
    *   Может предоставлять хук (`useUser`) или селекторы Redux для доступа к данным текущего пользователя после входа.

*   **Общие Компоненты (`shared/ui/`):**
    *   `Input.tsx`: Универсальный компонент поля ввода.
    *   `Button.tsx`: Универсальный компонент кнопки.
    *   `Tabs.tsx` или `ToggleLink.tsx`: Компонент для переключения форм.

*   **Состояние Аутентификации (`shared/lib/auth` или `app/providers/AuthProvider`):**
    *   Хук `useAuth()` или Redux slice (`authSlice`).
    *   Содержит состояние: `isAuthenticated` (boolean), `user` (объект пользователя или null), `token` (string или null), `isLoading` (boolean), `error` (string или null).
    *   Предоставляет функции для входа (`login(credentials)`), регистрации (`register(credentials)`), выхода (`logout()`). Эти функции взаимодействуют с API.

**5. API Дизайн: REST API для Аутентификации**

**Почему REST, а не WebSocket?**

*   **Природа Запросов:** Аутентификация (вход, регистрация) - это **кратковременные запросы типа "запрос-ответ"**. Пользователь отправляет данные, сервер проверяет их и возвращает результат (токен или ошибку). REST идеально подходит для такого взаимодействия.
*   **WebSocket:** Предназначен для **двунаправленной связи в реальном времени по постоянному соединению**. Он избыточен и неэффективен для однократных запросов аутентификации. WebSocket будет использоваться позже для отправки обновлений анализа после того, как пользователь войдет в систему.

**API Endpoints (Backend - Next.js API Routes):**

*   **`POST /api/auth/register`**
    *   **Назначение:** Регистрация нового пользователя.
    *   **Request Body (JSON):**
        ```json
        {
          "email": "user@example.com",
          "password": "yourSecurePassword123"
        }
        ```
    *   **Логика Backend:**
        1.  Валидация входных данных (email, сложность пароля).
        2.  Проверка, не занят ли email в базе данных (MongoDB, коллекция `Users`).
        3.  **Хеширование пароля** (использование `bcrypt`). **НИКОГДА не хранить пароли в открытом виде!**
        4.  Создание новой записи пользователя в коллекции `Users`.
    *   **Response Body (JSON - Успех, 201 Created):**
        ```json
        {
          "message": "User registered successfully"
          // Можно вернуть данные пользователя без пароля, если нужно
          // "user": { "id": "...", "email": "..." }
        }
        ```
    *   **Response Body (JSON - Ошибка, 400 Bad Request / 409 Conflict):**
        ```json
        {
          "error": "Validation failed" // или "Email already exists"
        }
        ```

*   **`POST /api/auth/login`**
    *   **Назначение:** Вход существующего пользователя.
    *   **Request Body (JSON):**
        ```json
        {
          "email": "user@example.com",
          "password": "yourSecurePassword123"
        }
        ```
    *   **Логика Backend:**
        1.  Валидация входных данных.
        2.  Поиск пользователя по email в коллекции `Users`.
        3.  Если пользователь найден, сравнение хеша введенного пароля с хешем в базе данных (используя `bcrypt.compare()`).
        4.  Если пароли совпадают, **генерация JWT (JSON Web Token)**. Токен должен содержать идентификатор пользователя (`userId`) и срок действия (`exp`). Использовать секретный ключ для подписи токена (хранить секретный ключ в переменных окружения!).
    *   **Response Body (JSON - Успех, 200 OK):**
        ```json
        {
          "token": "your_generated_jwt_token", // JWT
          "user": { "id": "...", "email": "..." } // Данные пользователя для UI
        }
        ```
    *   **Response Body (JSON - Ошибка, 400 Bad Request / 401 Unauthorized):**
        ```json
        {
          "error": "Invalid email or password"
        }
        ```

*   **(Опционально) `GET /api/auth/me`**
    *   **Назначение:** Получение данных текущего авторизованного пользователя.
    *   **Request Headers:** Требует заголовок `Authorization: Bearer <JWT>`.
    *   **Логика Backend:**
        1.  Извлечение JWT из заголовка.
        2.  Проверка валидности JWT (подпись, срок действия).
        3.  Извлечение `userId` из токена.
        4.  Поиск пользователя по `userId` в коллекции `Users`.
    *   **Response Body (JSON - Успех, 200 OK):**
        ```json
        {
          "user": { "id": "...", "email": "..." }
        }
        ```
    *   **Response Body (JSON - Ошибка, 401 Unauthorized):**
        ```json
        {
          "error": "Invalid or expired token"
        }
        ```

**6. Взаимодействие с Другими Компонентами/Модулями**

*   **`AuthFeature`** вызывает функции API (например, `api.login(credentials)`, `api.register(credentials)`), которые отправляют запросы на указанные эндпоинты.
*   После успешного входа, `AuthFeature` обновляет глобальное состояние аутентификации (через Redux `dispatch(authSlice.actions.loginSuccess({ user, token }))` или Auth Context).
*   Компоненты навигации (в `app/routes/`) или `AuthPage` сами используют состояние аутентификации (`useAuth()`) для выполнения перенаправлений.

**7. Безопасность**

*   **Хеширование паролей:** Обязательно использовать `bcrypt` или аналогичный надежный алгоритм для хеширования паролей перед сохранением в базу данных.
*   **HTTPS:** Все взаимодействие между клиентом и сервером должно происходить по HTTPS для шифрования трафика.
*   **JWT Security:**
    *   Использовать надежный секретный ключ для подписи JWT и хранить его безопасно (в переменных окружения).
    *   Устанавливать короткий срок действия (`exp`) для токенов (например, 15 минут - 1 час) и реализовывать механизм обновления токенов (refresh tokens), если требуется длительная сессия (для MVP можно начать без refresh token).
    *   Не хранить в JWT чувствительную информацию, кроме `userId` и `exp`.
*   **Валидация входных данных:** На backend всегда валидировать данные, приходящие от клиента.
